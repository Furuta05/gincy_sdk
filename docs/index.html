Что такое Gincy

Gincy — фундамент для разработки больших GMod-систем. Это не DarkRP, не готовый RP-режим и не новый язык. Это слой поверх GLua, который решает повторяющиеся технические задачи за тебя.

Если совсем просто: раньше ты сам следил за hook.Add, timer.Create, net.Receive, SQL, зависимостями и перезагрузкой. В Gincy ты говоришь модулю, что нужно сделать, а framework сам связывает это с жизненным циклом модуля, проверяет данные и умеет показать, где возникла проблема.

Это всё ещё GLua

Entities, players, hooks, VGUI, render, surface и остальные GMod API никуда не исчезают.

Open source

Core и native-часть можно изучать, собирать и расширять. Framework не требует строить сервер вокруг закрытой чёрной коробки.

Не привязан к RP

На Gincy можно строить RP, PvP, sandbox-системы, мини-игры или отдельные addons.

Сложность спрятана

Для обычной разработки есть Simple API. Context, ownership и низкоуровневые подсистемы нужны только когда тебе действительно нужен контроль.

Модуль за минуту

Для большинства кода начинать нужно не с ctx, а с Simple API:

local MOD = Gincy.Module("welcome")

MOD:Hook("PlayerInitialSpawn", function(ply)
    print("Welcome, " .. ply:Nick())
end)

MOD:After(5, function()
    print("Module is alive")
end)

Это уже полноценный Gincy-модуль. Зарегистрированные через него ресурсы принадлежат welcome. При unload/reload framework может убрать старые регистрации вместо того, чтобы оставлять забытые callbacks.

Главная идея: сначала пользуйся MOD:.... В Context лезь только тогда, когда Simple API тебе реально недостаточно.

Simple API сверху, мощный Core снизу

MOD:Every() выглядит как простой метод, но под ним работает ownership и Scheduler. MOD:Net() скрывает регистрацию route и schema. MOD:Content() создаёт принадлежащий модулю Content Type. Это один и тот же Core — Simple API не является второй параллельной системой.

local MOD = Gincy.Module("combat")

MOD:Every("cleanup", 30, {
    precision = "relaxed"
}, function()
    -- фоновая работа
end)

MOD:Net("select_skill", {
    skill = "string"
})

MOD:Receive("select_skill", function(ply, data)
    print(ply, data.skill)
end)

Scheduler вместо сотен независимых timers

Gincy имеет централизованный Scheduler. Задачи принадлежат модулю или Content, умеют автоматически отменяться, профилируются и не требуют линейно обходить все задачи каждый tick.

After

Одно выполнение через заданное время.

Every

Периодическая задача с именем, режимом точности и владельцем.

PlayersEvery

Типичный обход игроков без отдельного timer на каждого. Работу можно распределить между ticks.

Автоочистка

Unload модуля, reload Content или disconnect привязанного игрока отменяет принадлежащую работу.

MOD:PlayersEvery("status", 1, {
    spread = true,
    batch = 20
}, function(ply)
    -- Gincy может распределить игроков по ticks
end)

Module создаёт возможности. Content собирает из них игру.

Module — сама система: Combat, Inventory, HUD, Vehicles. Content — то, что часто меняется: конкретные skills, items, recipes, настройки HUD и другие определения.

local MOD = Gincy.Module("combat")

MOD:Content("skill", {
    name = "string",
    damage = "number",
    cooldown = "number"
})

После этого конкретный Fireball может жить отдельно от Combat:

-- gincy_content/combat/...
return {
    name = "Fireball",
    damage = 50,
    cooldown = 4
}
Зачем: добавление нового skill или изменение damage = 50 на 45 не должно требовать пересборки Combat.gmod. Сам модуль меняется, когда меняется механика или его публичные возможности.

Сложные Content Types могут дополнительно задавать validation, lifecycle и ограниченные capabilities. Content может иметь поведение, но получает только те возможности, которые ему открыл владелец типа.

Сеть без постоянного boilerplate

MOD:Net("equip", {
    item = "string"
})

MOD:Receive("equip", function(ply, data)
    -- data уже прошли schema validation
end)

MOD:Send("equip", ply, {
    item = "medkit"
})

Внутри остаётся полноценный Gincy Network: routes, schemas, rate limits, request/response, replicated state, streams, dictionaries и диагностика. Simple API нужен, чтобы для обычного сообщения не изучать всё это заранее.

Хранение данных

Для модуля можно создать собственное namespace-хранилище:

local users = MOD:Storage("users")

users:Set(ply:SteamID64(), {
    level = 12
}, function(ok, err)
end)

Storage остаётся асинхронным. PostgreSQL не является обязательным для Core, если активным модулям persistence не нужен. Для сложных случаев доступны repositories, transactions, migrations и низкоуровневый Storage API.

Ownership и reload

Главная причина существования Context внутри Gincy — знать, кому принадлежит ресурс. Simple API делает эту привязку автоматически.

MOD:Hook(...)       -- принадлежит Module
MOD:Every(...)      -- принадлежит Module
MOD:Net(...)        -- принадлежит Module
MOD:Content(...)    -- тип принадлежит Module

У Content есть собственное поколение и lifecycle. При неудачном hot reload новая версия отклоняется, а предыдущая рабочая версия может остаться активной. Подробнее про Context, поколения и cleanup — в API.

Разработка открытым GLua, production через .gmod

Во время разработки модуль остаётся обычным исходным кодом в gincy_dev/modules/. Production-модуль можно собрать в .gmod. Content при этом остаётся отдельно и не обязан упаковываться вместе с системой.

Чем Gincy не является

Не новый язык

Ты не обязан забывать GLua или GMod API.

Не RP framework

Core не диктует jobs, economy, characters или конкретный gameplay.

Не магическая оптимизация

Плохой callback останется плохим callback. Gincy даёт планирование, ownership и метрики, чтобы им было проще управлять.

Не абсолютный DRM

.gmod повышает стоимость извлечения и защищает поставку, но владелец машины теоретически может анализировать исполняемый процесс.
