Что такое Gincy

Gincy — слой между обычным GLua-кодом и инфраструктурой крупного сервера. Он не заставляет строить проект вокруг одной RP-схемы. Core знает, как загрузить модуль, проверить его требования, дать ему доступ только к заявленным возможностям, зарегистрировать принадлежащие ему объекты и корректно всё убрать при отключении или перезагрузке.

Проще: вы пишете механику. Gincy решает, как её подключить, связать с другими модулями, передать данные, сохранить состояние и безопасно перезагрузить.

Не DarkRP-база

Core не требует профессий, денег, персонажей или конкретного игрового режима. Такие системы могут быть подключаемыми модулями.

Обычный GLua

Разработчик продолжает использовать hooks, entities, VGUI и API Garry's Mod. Gincy добавляет структуру поверх них.

Модули знают свои границы

Manifest описывает зависимости, версию, точки входа и необходимые права.

Одна общая инфраструктура

Сеть, схемы, storage, команды и диагностика не размножаются в каждом аддоне.

Зачем это GLua-разработчику

На небольшом аддоне можно напрямую вызвать hook.Add, создать несколько net-сообщений и хранить таблицу в файле. На большом проекте появляется другая проблема: десятки систем должны запускаться в правильном порядке, не оставлять мусор после reload, проверять входящие данные одинаковым способом и не ломать друг друга.

Быстрый старт модуля

Модуль — обычная папка с manifest.lua и GLua-файлами. В manifest указываются версия, зависимости, права и точки входа.

return {
    id = "my_module",
    name = "My Module",
    author = "Developer",
    version = "1.0.0",
    requires = {
        gincy = ">=3.2.0 <4.0.0",
        api = ">=1.1.0 <2.0.0"
    },
    dependencies = {},
    capabilities = {"network.register"},
    reload = "MODULE_HOT_SWAP",
    entrypoints = {"sh_init.lua"}
}

Точки входа получают контекст модуля. Через него удобнее регистрировать всё, что должно исчезнуть вместе с модулем.

return function(ctx)
    ctx.Hooks:Add("PlayerSpawn", "welcome", function(ply)
        print("spawn:", ply)
    end)

    ctx.Timers:Create("heartbeat", 10, 0, function()
        print("module is alive")
    end)
end

Точная сигнатура точки входа зависит от загрузчика конкретного модуля; в API-разделе описаны публичные объекты контекста, найденные в Core.

Модули, зависимости и перезагрузка

Gincy хранит состояние загруженных модулей и умеет включать, отключать и перезагружать их. Контекст получает номер поколения: это позволяет отличать старые регистрации от новых при hot reload.

Capabilities

Модуль заранее заявляет, что ему нужно: например network.register, content.register или persistence.write. Контекст проверяет это перед регистрацией.

Ownership

Hooks, timers, network routes, content и другие записи привязываются к владельцу. Это снижает шанс оставить старый callback после reload.

Dependencies

Manifest может требовать другие модули с диапазоном версий. Core знает обратные зависимости и учитывает их при отключении.

Staged reload

Часть изменений может сначала подготавливаться, а затем активироваться. Для небезопасных случаев модуль может требовать restart.

Контент и схемы

Gincy разделяет код и данные. Модуль может объявить новый тип контента, а затем другие части проекта регистрируют записи этого типа. Это подходит не только для предметов: типом может быть способность, рецепт, состояние анимации, правило директора или ваша собственная сущность данных.

ctx.Content:RegisterType("quest", {
    type = "object",
    fields = {
        name = "string",
        reward = {type="number", min=0},
        repeatable = {type="boolean", default=false}
    }
}, "CONTENT_RELOAD", 1)

ctx.Content:Register("quest", "intro", {
    name = "Первое задание",
    reward = 100,
    repeatable = false
})

Schema поддерживает объекты, массивы, строки, числа, boolean, enum, entity, vector, angle и ссылки на другой content. Есть ограничения длины/диапазона и защита от слишком глубокой или огромной структуры.

Сеть

Сетевой слой Gincy работает поверх возможностей Garry's Mod и нужен для единообразной передачи данных между модулями. В исходниках есть типизированные маршруты, ограничение частоты, очередь, запрос/ответ, replicated state, delta, словари идентификаторов и передача больших данных частями.

Маршруты

Сообщение получает ID, schema, rate limit и handler. Данные проверяются до вызова игровой логики.

Request / response

Network.Request связывает запрос с callback и timeout вместо ручного придумывания ID ответа.

Состояние

RegisterState и PublishState предназначены для синхронизируемого состояния с revision.

Streams

Большие payload разбиваются на ограниченные части; Core отслеживает передачу и позволяет отменять её.

Важно: это не замена сетевого транспорта Source Engine. Gincy организует данные и уменьшает типичные ошибки поверх существующей сети GMod.

Хранение данных

Persistence подключается только когда она нужна. Если активные модули не требуют БД, отсутствие PostgreSQL не должно мешать остальному Core. Для модулей доступны namespace-хранилища, Get/Set, транзакции и SQL-миграции.

local users = ctx.Storage:Register("users", {
    -- schema репозитория
})

users:Get("steamid", function(ok, err, value)
    -- результат приходит callback'ом
end)

Native-часть выполняет работу с PostgreSQL вне основного игрового потока, а Lua забирает готовые результаты. Миграции идут последовательно и сохраняют контрольные суммы, чтобы уже применённый SQL не менялся незаметно.

Как это выглядит в реальной разработке

Главная идея Gincy — защита и инфраструктура не должны мешать писать аддон. Во время разработки у вас остаётся обычный GLua-проект: файлы можно читать, менять, перезагружать и нормально отлаживать. Защищённый .gmod появляется только тогда, когда модуль готов к публикации или установке на production-сервер.

1Dev-версия

Пишете обычный GLua в gincy_dev/modules/MyAddon/. Никакого шифрования во время работы.

→
2Ваш аддон

Manifest, server/client/shared код, контент и зависимости остаются нормальным проектом, который удобно править.

→
3Сборка

Gincy Builder проверяет модуль и собирает production-пакет.

→
4MyAddon.gmod

Код и служебные данные упакованы, подписаны и защищены согласно policy модуля.

→
5GincyCore

Core проверяет пакет и может загрузить защищённый код напрямую через runtime без ручной распаковки исходников.

gincy_dev/modules/MyAddon/
        │
        │  обычная разработка и hot reload
        ▼
     MyAddon
        │
        │  production build
        ▼
 MyAddon-1.0.0.gmod
        │
        │  verify → load protected entries
        ▼
     GincyCore
        │
        └─→ модуль работает на сервере
Что важно: разработчику не нужно писать отдельную «зашифрованную версию» аддона. Защита — этап сборки. Исходный проект остаётся удобным для разработки, а на production можно отдавать уже .gmod.

.gmod: доставка и защита модулей

Package Format 2 — отдельный контейнер Gincy. Он хранит manifest, список файлов, сведения о защите и подпись. Проверка пакета происходит до исполнения.

Подпись и целостность

Контейнер подписывается; изменение manifest, policy или payload должно ломать проверку.

Server protection

Для защищённых server entries используется отдельная обработка и шифрование; runtime может расшифровывать entry в памяти.

Client GVM

В текущем source присутствуют компилятор и Lua runtime GVM: protected client entry может храниться как собственное представление вместо исходного GLua. Клиентская DLL для GVM не требуется.

Recipient binding

Package API предусматривает привязку protected payload к ключу получателя, а также fingerprint metadata.

Граница защиты: код, который выполняется на машине владельца сервера или игрока, нельзя сделать математически недоступным для человека, полностью контролирующего процесс. Защита Gincy должна рассматриваться как барьер против простого копирования и как усложнение анализа, а не как обещание «невозможно достать».

Что важно знать о текущем source

Сайт описывает возможности, которые реально видны в переданном архиве. При этом сам архив содержит следы нескольких этапов разработки: корневая папка называется 3.0.0-rc1, старый manual подписан как 3.1.0, а канонический version.json уже объявляет Product 3.2.0, Framework API 1.1.0, Native ABI 2 и Package Format 2.

В source уже есть GVM runtime/compiler и Package V2 tests, но старый manual всё ещё описывает более раннюю защиту, где client/shared оставались читаемыми. Поэтому при расхождении этот сайт ориентируется на текущий код 3.2.0, а не на старый текст manual.

Для разработчика: используйте страницу API как карту публичных точек входа. Для поведения, критичного к версии, сверяйтесь с исходником конкретного релиза.
