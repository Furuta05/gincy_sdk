Пиши аддон как обычно. Gincy убирает за тобой хуки, таймеры и сеть.

Gincy не заменяет Lua и не учит новому языку. Ты по-прежнему вызываешь PlayerSpawn, читаешь ply:Nick() и пишешь обычные функции. Разница в том, что хук, повтор задачи и сетевое сообщение можно повесить на модуль: при перезагрузке модуля Gincy их снимет.

Что такое Gincy

Gincy — каркас для серверных систем Garry's Mod. Боевая система, инвентарь, HUD, работы, транспорт: каждая такая система живёт отдельным модулем. Игровые числа, которые ты меняешь каждую неделю — урон фаербола, цена предмета, цвет HUD — лежат отдельно, в контенте, и не требуют новой сборки модуля.

Обычный аддон на hook.Add и timer.Create продолжает работать. Gincy нужен, когда таких аддонов несколько и их надо выключать, обновлять и не оставлять старые таймеры после перезагрузки.

Что он берёт на себя

Модуль

Одна система: код, хуки, сеть и правила для контента. На сервере это папка dev или файл .gmod в production.

Контент

Открытые файлы навыков, предметов, рецептов. Их можно поменять, не пересобирая модуль.

Задачи по времени

Один общий планировщик вместо сотен timer.Create. Задача помнит, какому модулю она принадлежит.

Сеть

Сообщение описывается полями. Чужой тип или лишний ключ не попадает в твою функцию.

Сохранения

PostgreSQL по желанию. Если ни один модуль его не просит, сервер спокойно работает без базы.

Пакет .gmod

Готовый модуль для выдачи на сервер. Исходники контента в этот файл класть не нужно.

Пример за минуту

В консоли сервера:

gincy create module stamina

Появится папка garrysmod/gincy_dev/modules/stamina/ с manifest.lua и sh_init.lua. В sh_init.lua уже есть Gincy.Module("stamina"). Дальше ты дописываешь хуки и задачи так, как в блоке справа вверху.

Пока сервер в режиме разработки (gincy/runtime.json, поле development равно true), Gincy читает модули из gincy_dev/modules. Готовые пакеты он читает из gincy_modules/*.gmod.

С чего начать в справочнике: Gincy.Module, затем MOD:Hook и MOD:Every.

Это всё ещё GLua

Обычный хук:

hook.Add("PlayerSpawn", "Stamina.Spawn", function(ply)
    ply:SetNWInt("Stamina", 100)
end)

Тот же хук через модуль:

MOD:Hook("PlayerSpawn", function(ply)
    ply:SetNWInt("Stamina", 100)
end)

hook.Add остаётся в игре навсегда, пока ты сам не вызовешь hook.Remove. MOD:Hook делает тот же hook.Add, но запоминает имя хука. Когда модуль выгружают или перезагружают, Gincy вызывает hook.Remove сам.

То же с временем. timer.Create живёт, пока его не удалят. MOD:Every ставит задачу в общий планировщик Gincy, и при выгрузке модуля задача отменяется.

Задачи по времени

MOD:After(5, fn) — один раз через 5 секунд. MOD:Every(1, fn) — снова и снова раз в секунду. MOD:PlayersEvery обходит игроков одним общим тиком, а не отдельным таймером на каждого человека.

Если игрок вышел, задача, привязанная к нему, больше не вызывается. Если функция 8 раз подряд падает с ошибкой, планировщик её выключает и пишет это в консоль, а остальные задачи продолжают идти.

Смотреть, кто грузит сервер: gincy scheduler и gincy scheduler inspect имя.

Модуль и контент

Модуль — это код системы. Контент — это данные, которые эта система читает.

Combat.gmod          -- код боя, его редко пересобирают
gincy_content/combat/skill/fireball.lua
gincy_content/combat/skill/dash.lua

Модуль один раз объявляет, какие поля есть у навыка. Файл навыка просто возвращает таблицу: имя, урон, перезарядка. Добавить молнию — значит положить новый файл. Combat.gmod из-за этого заново не собирается и не перезагружается.

Если в новой версии файла написано cooldown = "fast", а поле должно быть числом, Gincy не подменяет рабочий навык. Старый фаербол остаётся, ошибка пишется в диагностику.

Сеть

Вместо ручного net.WriteString ты описываешь поля:

MOD:Net("select_skill", { skill = "string" })

MOD:Receive("select_skill", function(ply, data)
    print(data.skill)
end)

Имя на проводе будет stamina.select_skill, если модуль называется stamina. Чужое поле или строка вместо числа до твоей функции не дойдут. Лимит скорости для такого сообщения — 8 в секунду, направление сразу в обе стороны. Это значения, которые ставит MOD:Net. Более тонкая настройка есть у ctx.Network:Register.

Сохранения

База не обязательна. Если ни один включённый модуль не просит запись, состояние «PostgreSQL не настроен» — не поломка сервера.

Простое сохранение:

local players = MOD:Storage("players")
players:Set(steam, { stamina = 40 }, function(ok) end)
players:Get(steam, function(ok, value) end)

Вызов не останавливает сервер в ожидании базы. Ответ приходит в функцию, которую ты передал последним аргументом. Пароль Gincy не печатает ни в gincy storage status, ни в JSON.

Перезагрузка

У каждой загрузки модуля есть свой набор созданных вещей: хуки, задачи, сетевые обработчики, типы контента. При gincy module reload имя старый набор снимается, затем выполняется новый код. Горячая перезагрузка срабатывает только если в manifest.lua написано reload = "MODULE_HOT_SWAP". Иначе команда вернёт, что нужен перезапуск карты.

Смена файла контента модуль не перезагружает. Меняется только этот навык или предмет.

Файл .gmod

.gmod — это собранный модуль для сервера, а не контейнер для каждого фаербола. Сборка:

gincy package build garrysmod/gincy_dev/modules/stamina --key signer.pem

Готовый файл попадает в garrysmod/gincy_modules/stamina.gmod. Без флагов режим open: сервер компилирует код как обычный Lua. --protected закрывает файлы модуля. --maximum дополнительно собирает клиентский код во внутреннюю программу GVM. Контент в gincy_content при этом остаётся обычными lua-файлами.

Чего Gincy не делает

Не новый язык

if, function, player.GetAll и SWEP пишутся как раньше.

Не готовый DarkRP

Работы, экономика и персонажи — это уже твои модули, не ядро.

Не ускоряет плохой код

Тяжёлая функция останется тяжёлой. Gincy только не даёт ей свалить остальные задачи и показывает, сколько она ест.

Не прячет сервер от владельца машины

Пакет с --protected усложняет копирование модуля. Это не абсолютная защита процесса.

Дальше каждая функция разобрана отдельно: открыть API.
