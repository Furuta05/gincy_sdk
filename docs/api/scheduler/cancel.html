Снимает задачу по id, по владельцу, по контенту или по сущности.

Зачем это нужно. Обычно снимать руками не нужно: модуль и контент делают это при выгрузке. Явный Cancel нужен, если бафф кончился раньше, чем модуль.

Где это встречается на сервере

  • Игрок снял бафф, именная задача ещё жива.
  • Запись контента удалена твоим кодом раньше reload.

Синтаксис

Gincy.Scheduler.Cancel(id)
Gincy.Scheduler.CancelOwner("stamina", generation)
Gincy.Scheduler.CancelContent("combat.skill/fireball", generation)
Gincy.Scheduler.CancelEntity(ply)

generation необязателен. Если передан, снимутся только задачи этого номера.

Что означает каждая часть

  • id — Строка, которую вернул Schedule, Every или After.
  • owner — id модуля.
  • content — Строка тип/id, как её пишет контент в задачу.
  • entity — Тот же объект игрока, который передавали в Every.

Аргументы

АргументТипОбязательныйПо умолчаниюЧто передавать
idстрокада для CancelнетНеизвестная строка просто вернёт false.
generationчислонетснять все номераСовпадает с ctx.generation или с номером экземпляра контента.

Что возвращается

true, если задача была и её сняли. false, если id уже нет. CancelOwner и остальные ничего полезного не возвращают: они проходят список.

Что происходит после вызова

Функция больше не вызовется. Запись выкидывается из расписания. Сущность при этом не Remove.

Перезагрузка и выгрузка

Повторная отмена безопасна: второй Cancel вернёт false.

Ограничения

  • CancelEntity снимает все задачи, куда передали этот объект, не только одного модуля.
  • Отмена не откатывает то, что функция уже успела сделать в мире.

Рядом обычно вызывают

  • Schedule — Откуда берётся id.

Конец баффа

local id = MOD:After(10, function()
    ply:SetNWBool("Shield", false)
end)
-- игрок снял щит сам через 2 секунды
Gincy.Scheduler.Cancel(id)
ply:SetNWBool("Shield", false)

Через оставшиеся 8 секунд повторного снятия не будет. NWBool ты ставишь сам, Cancel только не даёт старому After сработать ещё раз.
