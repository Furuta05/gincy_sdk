Разрешение — строка вроде network.register. Её автор модуля сам вписывает в capabilities. Require останавливает код, если строки нет. Это защита от модуля, который полез в сеть, хотя обещал только рисовать HUD.

Зачем это нужно. Перед регистрацией сети, контента или базы. Готовые MOD:Net и MOD:Content вызывают проверку сами.

Где это встречается на сервере

  • Свой код вызывает ctx.Network:Register.
  • Модуль без базы не должен молча писать в PostgreSQL.

Синтаксис

ctx:Require("network.register")

Строка ровно как в manifest.

Что означает каждая часть

  • cap — Имя разрешения. Список не зашит в ядро целиком: проверяется наличие в capabilities этой загрузки. Какие строки ждут встроенные методы, видно по их страницам: network.register, content.register, persistence.read, persistence.write, commands.register и имена реестров вроде services.register.

Аргументы

АргументТипОбязательныйПо умолчаниюЧто передавать
capстрокаданетЕсли его нет или ctx закрыт, вызов делает error с текстом «модуль requires ...».

Что возвращается

Ничего, если проверка прошла.

Что происходит после вызова

Дальнейший код выполняется только после успешной проверки. Игрокам сообщение не шлётся.

Перезагрузка и выгрузка

На закрытой загрузке проверка тоже падает, даже если строка в manifest была.

Ограничения

  • Простой Gincy.Module выдаёт себе network.register, content.register, persistence.read и persistence.write. commands.register среди них нет: команда через ctx.Commands попросит commands.register.
  • Опечатка в строке равна отсутствию разрешения.

Рядом обычно вызывают

  • capabilities — Куда вписать строку.

Сеть только если разрешена

ctx:Require("network.register")
ctx.Network:Register("ping", {
    schema = { ok = "boolean" },
    rate = 2,
    direction = "c2s"
}, function(ply, data)
    print(data.ok)
end)

Если в manifest нет network.register, выполнение файла остановится на Require и канал не появится. Если есть, канал будет называться idМодуля.ping.
