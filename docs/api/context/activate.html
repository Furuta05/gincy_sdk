ctx:Activate

Включает отложенные регистрации, когда модуль уже прошёл подготовку.

Пока файлы модуля только читаются, часть регистраций ждёт в очереди, чтобы половинчатый модуль не светился игрокам. Activate выполняет очередь. Загрузчик вызывает это сам. Вручную нужно только если ты сам создал ctx в состоянии подготовки.

Зачем это нужно. Редкий код, который собирает модуль не через обычный файл, а своим загрузчиком.

Где это встречается на сервере

  • Свой тестовый загрузчик.
  • Понимание, почему хук не виден до конца Initialize.

Синтаксис

ctx:Activate()

Без аргументов.

Что означает каждая часть

  • ctx — Загрузка, которую создавали с подготовкой. Обычный Gincy.Module создаёт уже активную загрузку, и вызов просто ещё раз прогонит пустую очередь.

Что возвращается

Ничего.

Что происходит после вызова

Флаг active становится истиной. Каждая отложенная пара Own выполняется, уборка переносится в список. Очередь очистки.

Перезагрузка и выгрузка

Повторный Activate на пустой очереди ничего не дублирует. Shutdown после этого всё равно снимет то, что успели включить.

Ограничения

  • Не вызывай Activate в середине файла, если рассчитываешь, что следующие Own ещё подождут. После неё новые Own включаются сразу.

Рядом обычно вызывают

  • Shutdown — Обратное действие.
  • Own — Что именно копится в очереди.

Подготовка

local ctx = Gincy.Internal.Context({ id = "temp", capabilities = {} }, true)
ctx:Own(function() print("включён") end, function() print("снят") end)
-- пока тишина
ctx:Activate()
-- печать «включён»

Второй аргумент true у внутреннего конструктора значит «ещё готовимся». Own не печатает, пока нет Activate. Обычному модулю этот конструктор не нужен: Gincy.Module и загрузчик вызывают нужное сами. Internal не является стабильной игровой дверью, пример только показывает порядок.
