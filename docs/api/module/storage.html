MOD:Storage("players") не заставляет читать пул соединений и SQL. Оно возвращает объект с Get и Set. База при этом остаётся асинхронной: сервер не замирает на запросе.

Зачем это нужно. Запомнить стамину игрока между рестартами. Запомнить открытые рецепты.

Где это встречается на сервере

  • Таблица игроков по SteamID.
  • Один ключ настроек гильдии.

Синтаксис

local players = MOD:Storage("players")

players:Set("76561190000000000", { stamina = 40 }, function(ok, err, value)
    if not ok then print(err and err.code) end
end)

players:Get("76561190000000000", function(ok, err, value)
    if ok and value then print(value.stamina) end
end)

Имя хранилища короткое. Полное имя внутри — idМодуля.players.

Что означает каждая часть

  • name — Короткое имя. Правило идентификатора: строчные буквы, цифры, _, точка, двоеточие, до 96 символов.
  • Set — Аргументы key, value, callback.
  • Get — Аргументы key и callback. Ответ приходит позже, не в return.
  • callback — Ей приходят ok, err, value. Если ok ложь, err — таблица с полем code.

Аргументы

АргументТипОбязательныйПо умолчаниюЧто передавать
nameстрокаданетИмя внутри модуля. Пустая схема: можно класть не только таблицу, а любое значение, которое уложится в JSON до 16384 байт.

Что возвращается

Объект с методами Get и Set. Не данные игрока. Данные приходят только в callback.

Что происходит после вызова

Регистрация запоминается за номером загрузки. Set и Get ставят запрос в очередь базы. Если PostgreSQL не готов, callback получит неудачу, кадр сервера это не держит. Пока загрузка модуля не активна, Set из ещё не включённого контекста запрещён.

Перезагрузка и выгрузка

Выгрузка снимает регистрацию схемы этого имени. Уже лежащие в базе строки сами по себе не стираются: снимется только право этой загрузки писать через этот объект.

Ограничения

  • Нужны разрешения persistence.read и persistence.write. У Gincy.Module они есть. В manifest их надо перечислить, иначе Require остановит модуль.
  • Ключ — идентификатор, не произвольный текст с пробелами.
  • Пароль в callback и в ошибку не подставляется.
  • Если база не настроена, а модуль объявил такие разрешения, загрузчик держит модуль в ожидании хранилища, а не притворяется, что запись удалась.

Рядом обычно вызывают

  • Gincy.Storage.Get — Тот же запрос без объекта.
  • storage setup — Как поднять базу.

Стамина между рестартами

local store = MOD:Storage("players")

MOD:Hook("PlayerDisconnected", function(ply)
    store:Set(ply:SteamID64(), { stamina = ply:GetNWInt("Stamina", 0) }, function(ok)
        if not ok then print("стамина не сохранилась") end
    end)
end)

MOD:Hook("PlayerInitialSpawn", function(ply)
    store:Get(ply:SteamID64(), function(ok, err, value)
        local stamina = (ok and value and value.stamina) or 100
        ply:SetNWInt("Stamina", stamina)
    end)
end)

При выходе число уходит в базу ключом SteamID64. При следующем входе callback получает таблицу и ставит NWInt. Пока ответ не пришёл, игрок уже может быть в игре: поставь временные 100, если value ещё нет. При unload модуля хуки снимутся, строки в PostgreSQL останутся.
