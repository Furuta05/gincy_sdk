Модуль один раз говорит, что такое combat.skill. Дальше файлы в gincy_content только заполняют поля. Ядро само не знает слов «навык» и «предмет».

Зачем это нужно. Боевая система публикует навыки. Инвентарь публикует предметы. HUD публикует тему, но не отдаёт свой код.

Где это встречается на сервере

  • Поля name, damage, cooldown.
  • Тип с проверкой «урон не больше 500» и с методом Explode для файлов навыков.

Синтаксис

MOD:Content("skill", {
    name = "string",
    damage = "number",
    cooldown = "number"
})

Короткое имя станет idМодуля.skill, если точки в имени нет.

MOD:Content("skill", {
    schema = {
        name = "string",
        damage = "number",
        cooldown = "number"
    },
    capabilities = {
        Explode = function(skill, amount)
            -- код модуля, файл навыка сам эту таблицу не видит
        end
    },
    validate = function(data)
        if data.damage > 500 then return false end
        return true
    end,
    load = function(inst, proxy) end,
    reload = function(inst, old) end,
    unload = function(inst) end
})

Длинная форма. Она включается, если в таблице есть schema, capabilities или функции validate, load, prepare, reload, unload.

Что означает каждая часть

  • skill — Короткое имя. Превратится в combat.skill для модуля combat. Если имя уже с точкой, приставка не добавляется, но часть до точки обязана равняться id модуля. Иначе ошибка: пространство принадлежит другому.
  • name = "string" — Поле и тип. Типы схемы перечислены на странице схемы.
  • capabilities — Таблица функций, которые файл контента сможет звать через объект навыка. Это не права CAMI.
  • validate — Функция проверки уже разобранных полей. false или ошибка отклоняют запись.
  • load или prepare — Вызов перед тем, как запись станет активной. Сюда приходит экземпляр и прокси.
  • reload — Вызов после успешной подмены старой записи новой.
  • unload — Вызов, когда экземпляр снимают.

Что возвращается

Строка полного типа, например combat.skill.

Что происходит после вызова

Тип регистрируется за этим модулем с политикой CONTENT_RELOAD и версией схемы 1. Уже существующий тип того же владельца повторно не создаётся: вернётся ошибка. Чужой модуль занять префикс не может. После регистрации подхватываются уже найденные файлы этого типа.

Перезагрузка и выгрузка

Выгрузка модуля снимает тип, если на нём не осталось живых записей. Записи контента этого владельца отпускаются, их задачи отменяются. Сами файлы на диске не удаляются.

Ограничения

  • Нужно разрешение content.register.
  • Простая форма не открывает файлу функции. Пока в capabilities нет Schedule или After, у навыка не будет :After и :Every.
  • Поля-функции из файла контента в сохранённую таблицу данных не копируются. Их вызывает Gincy.Content.Call.

Рядом обычно вызывают

  • Файл навыка — Что возвращает lua.
  • Активация — Почему сломанный файл не затирает старый.

Навык

local MOD = Gincy.Module("combat")

MOD:Content("skill", {
    name = "string",
    damage = "number",
    cooldown = "number"
})

После этого gincy_content/combat/skill/fireball.lua может вернуть name, damage и cooldown. Строка в cooldown не станет активной. Добавление lightning.lua не требует новой сборки Combat.gmod.

Закрытый HUD

MOD:Content("config", {
    schema = { accent = "string", scale = "number" },
    capabilities = {}
})

Файл темы может задать accent и scale. Поле implementation, даже если его вернуть из файла, не превращается в доступ к коду HUD: в прокси попадают только данные и те методы, которые модуль явно положил в capabilities.
