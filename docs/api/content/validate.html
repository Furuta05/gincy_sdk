Проверяет таблицу по типу и ничего не включает.

Зачем это нужно. Удобно спросить «эти поля годные?» до Activate. Неизвестный тип, кривой id или поле не того типа дают false и ошибку.

Где это встречается на сервере

  • Админская команда проверяет черновик.
  • Свой редактор предмета перед сохранением.

Синтаксис

local ok, value = Gincy.Content.Validate("combat.skill", "fireball", {
    name = "Fireball",
    damage = 50,
    cooldown = 4
})

При успехе value — копия с служебным _schemaVersion. Его не надо писать в файл.

Что означает каждая часть

  • kind — Тип должен быть уже зарегистрирован.
  • id — Проверяется как идентификатор, даже если в полях его нет.
  • definition — Таблица полей. Лишние ключи схема отвергает.

Аргументы

АргументТипОбязательныйПо умолчаниюЧто передавать
kindстрокаданетИначе GINCY-CONTENT-TYPE.
idстрокаданетПравило идентификатора.
definitionтаблицаданетНе функция и не строка.

Что возвращается

true и нормализованная таблица, либо false и ошибка. Запись в игре не появляется.

Что происходит после вызова

Если для типа регистрировали миграции схемы, они применяются к копии до проверки полей.

Перезагрузка и выгрузка

Ничего не снимает, потому что ничего не включает.

Ограничения

  • Не заменяет Activate. После Validate файл всё ещё не активен.
  • Сообщение схемы похоже на путь поля, например $.cooldown: numeric range/type.

Рядом обычно вызывают

  • Schema.Validate — Проверка без типа контента.
  • MigrateType — Как старые таблицы дотягиваются до новой.

Проверка до выдачи

local ok, value = Gincy.Content.Validate("inventory.item", "bread", {
    name = "Bread",
    price = "пять"
})
if not ok then print(value.message) end

price строка не пройдёт, если поле объявлено number. Предмет в магазине не изменится, игрок ничего не купит по ошибке.
