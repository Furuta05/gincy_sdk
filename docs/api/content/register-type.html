Объявляет тип контента без обёртки MOD:Content. Обычному модулю хватает MOD:Content.

Зачем это нужно. Функция ядра проверяет схему, владельца и конфликт имён. MOD:Content собирает аргументы и вызывает её.

Где это встречается на сервере

  • Свой загрузчик типов.
  • Понимание ошибки GINCY-CONTENT-NAMESPACE.

Синтаксис

Gincy.Content.RegisterType("combat.skill", {
    type = "object",
    fields = { name = "string", damage = "number", cooldown = "number" }
}, "combat", "CONTENT_RELOAD", 1)

Владелец — id модуля. Если в имени типа есть точка, текст до точки обязан совпасть с владельцем.

Что означает каждая часть

  • kind — Полное имя типа.
  • schema — Уже нормальная схема с type и fields, не короткая таблица MOD:Content. Короткую форму понимает только MOD:Content.
  • owner — id модуля.
  • policy — Строка, по умолчанию CONTENT_RELOAD. Хранится в типе и показывается в content types.
  • version — Число версии схемы. Нечисло становится 0.
  • advanced — Необязательная таблица capabilities, prepare или load, reload, unload, validate.

Аргументы

Что возвращается

true или false плюс ошибка. Ошибка — таблица с code и message.

Что происходит после вызова

Тип появляется в Gincy.Content.Types. Повтор того же владельца отвергается. Чужой владелец отвергается. Уже лежащие на диске файлы этого типа подхватываются, если обход контента уже готовил очередь.

Перезагрузка и выгрузка

UnregisterType снимает тип только если записей этого типа не осталось и владелец совпал. Иначе NOT_OWNER или GINCY-CONTENT-DEPENDENTS.

Ограничения

  • Не вызывай вместе с MOD:Content на тот же тип: второй вызов увидит, что тип занят.
  • Короткие поля name = "string" здесь не разворачиваются сами.

Рядом обычно вызывают

  • MOD:Content — Короткая форма.
  • Schema.Check — Что считается годной схемой.

Конфликт

Gincy.Content.RegisterType("combat.skill", { type = "object", fields = {} }, "inventory")

Вернётся неудача: префикс combat принадлежит combat, а владелец указан inventory. Тип инвентаря не перехватит навыки боя молча.
