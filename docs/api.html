Как пользоваться API

У Gincy два уровня. Simple API — нормальный выбор для большинства модулей. Advanced API открывает Context, низкоуровневую сеть, schema, storage и lifecycle.

local MOD = Gincy.Module("example")

MOD:Hook("PlayerSpawn", function(ply)
end)

MOD:Every("update", 1, function()
end)
Правило: если задачу можно решить через MOD:..., используй его. ctx нужен, когда требуется функция, которой нет в facade, или когда ты пишешь инфраструктурный/сложный модуль.

Gincy.Module и Simple API

Gincy.Module(id)

local MOD = Gincy.Module("combat")

Возвращает facade текущего Module Context. ID: lowercase, начинается с буквы, далее буквы/цифры/_. В загружаемом модуле ID должен совпадать с текущим context.

MOD:Hook(event, [id], fn) / MOD:On(...)

MOD:Hook("PlayerSpawn", function(ply) ... end)

Регистрирует GMod hook через ownership текущего модуля. Если ID не передан, используется имя event. On — alias. Hook удаляется при shutdown поколения модуля.

MOD:After(delay, fn)

local handle = MOD:After(5, callback)

Одноразовая gameplay-задача Scheduler с точностью exact. Возвращает handle задачи.

MOD:Every(...)

MOD:Every(interval, fn)
MOD:Every(name, interval, fn)
MOD:Every(name, interval, options, fn)
MOD:Every(entity, name, interval, fn)
MOD:Every(entity, name, interval, options, fn)

Периодическая задача. Options поддерживают precision, class, mode. Entity-owned задача автоматически связывается с Entity и по умолчанию считается gameplay/exact.

MOD:PlayersEvery(name, interval, [options], fn)

MOD:PlayersEvery("status", 1, {spread=true, batch=20}, function(ply) ... end)

Периодическая обработка игроков. spread=true позволяет распределять работу, batch задаёт размер партии.

MOD:Net(name, schema)

MOD:Net("equip", {item="string"})

Регистрирует типизированный route module.name через Gincy Network. Simple route использует schema validation и стандартный rate limit.

MOD:Receive(name, fn)

MOD:Receive("equip", function(ply, data) ... end)

Назначает handler ранее объявленного Simple Network route.

MOD:Send(name, ply, data)

Проверяет outgoing data по schema и отправляет через Gincy Network.

MOD:Content(name, spec)

MOD:Content("skill", {name="string", damage="number"})

Регистрирует Content Type в namespace модуля: combat.skill. Простая таблица означает schema fields. Расширенный spec может содержать schema, capabilities, validate, load, prepare, reload, unload.

MOD:LoadContent(kind, id, definition, [info])

Активирует Content через Content Runtime и связывает его с текущим module generation. Обычно production content обнаруживается loader'ом; метод полезен для программной загрузки и тестов.

server

MOD:Storage(name)

local repo = MOD:Storage("users")

Создаёт repository module.name через текущий Context и возвращает объект с Get/Set.

MOD:Context()

Возвращает underlying Context. Это мост из Simple API в Advanced API.

MOD:Unload()

Завершает Context, очищает owned resources, Content и module storage registrations и переводит модуль в disabled state.

Gincy.Scheduler

Централизованный планировщик Gincy. Simple API After/Every/PlayersEvery использует именно его; это не отдельный timer.Create на каждую задачу.

Gincy.Scheduler.Schedule(spec)

Создаёт задачу. Spec может содержать name, owner, moduleGeneration, content, contentGeneration, delay/interval, reps, entity, kind="players", spread, batch, precision, class, mode, source, fn.

Cancel(handle)

Отменяет одну задачу.

CancelOwner(owner, [generation])

Удаляет задачи владельца; используется lifecycle модулей.

CancelContent(content, [generation])

Удаляет задачи конкретного Content instance/generation.

CancelEntity(entity)

Удаляет задачи, связанные с Entity. Scheduler также подключён к PlayerDisconnected.

Configure(options)

Настраивает runtime scheduler, включая budget.

Inspect(query) / Snapshot() / Stats() / CountOwner(owner)

Диагностика задач и метрик. Snapshot используется CLI/Management.

Benchmark(count)

Встроенный benchmark scheduling infrastructure; в source также есть scheduler benchmark test.

Внутренние/test API: Tick, SetNow и переопределение Measure существуют для runtime/tests. В игровом модуле обычно их вызывать не нужно.

Content через Module

Content Type принадлежит Module. Core не знает, что такое skill или item — это определяет владелец namespace.

local MOD = Gincy.Module("combat")

MOD:Content("skill", {
    name = "string",
    damage = "number",
    cooldown = "number"
})

Content Runtime разделяет данные и функции, проверяет schema и зависимости, создаёт instance generation и может выполнить lifecycle типа. В definition специальные поля depends и uses используются runtime, если они не объявлены обычными schema fields.

Advanced Content spec

MOD:Content("skill", { schema=..., capabilities=..., validate=..., prepare=..., load=..., reload=..., unload=... })

capabilities определяет методы, доступные proxy конкретного Content. Если тип разрешает scheduling capability, proxy получает :After/:Every, а задачи привязываются к generation Content и очищаются при замене.

Network через Module

Simple API подходит для обычных route. Если нужны state, streams, request/response, dictionaries или особые параметры route — используй ctx.Network и Gincy.Network.

Storage через Module

local users = MOD:Storage("users")
users:Get(key, callback)
users:Set(key, value, callback)

Callbacks не вызываются через закрытый Context. Для транзакций и прямого namespace API используй ctx.Storage.

Что такое ctx (Context)

ctx — объект жизненного цикла конкретного поколения модуля. Его задача — знать кто создал ресурс и как этот ресурс убрать.

Когда модуль перезагружается, старый Context закрывается. Gincy проходит его cleanup в обратном порядке, отменяет scheduler tasks и чистит network registrations. Новый экземпляр модуля получает новое generation.

Поэтому Context — не обязательная философия, которую нужно учить до первого модуля. Это механизм ownership под Simple API. Получить его вручную можно через MOD:Context().

Context lifecycle

ctx:Require(capability)

Проверяет capability текущего модуля. При отсутствии права операция останавливается.

ctx:Defer(callback)

Добавляет cleanup callback. Используй для собственного ресурса, для которого нет готовой Gincy-обёртки.

ctx:Own(apply, remove)

Регистрирует пару создания/удаления. В staged context операция может ждать activation; после применения remove попадает в cleanup.

ctx:Activate()

Активирует staged context и применяет pending registrations.

ctx:Shutdown()

Закрывает Context, выполняет cleanup, отменяет scheduler/network resources текущего generation.

ctx:GetLogger()

Logger с Info, Warn, Error, Debug и префиксом модуля.

Hooks, timers и registries через ctx

ctx:Hook(event, id, fn) / ctx.Hooks:Add(...)

Owned GMod hook. Фактический key включает module ID и generation.

ctx:Timer(id, delay, repetitions, fn) / ctx.Timers:Create(...)

Compatibility API таймера, но реализация идёт через Gincy Scheduler. Delay не меньше 0.01; repetitions=0 означает повторение без заданного конца.

Registry proxies

Context создаёт owned proxies для зарегистрированных Gincy registries. Они предоставляют Register, Get, Exists; часть registries также получает aliases вроде RegisterType/RegisterRule/RegisterModifier. Регистрация проверяет соответствующую capability.

ctx.Network

ctx.Network:Register(id, definition, handler)

Owned route с полным ID module.id. Требует network.register. Definition передаётся существующему Network registry.

ctx.Network:RegisterState(id, schema, onChange)

Регистрирует replicated state модуля. Текущая реализация помечает context как restart-required для безопасного изменения структуры.

ctx.Network:RegisterStream(id, handler, options)

Owned stream для больших данных. Также помечает context как restart-required.

ctx.Content

RegisterType(kind, schema, policy, schemaVersion, [advanced])

Низкоуровневая регистрация Content Type. Требует content.register, проверяет schema и связывает type с owner.

Register(kind, id, definition)

Регистрирует owned content record через базовый registry.

Get(kind,id) / GetAll(kind) / Exists(kind,id)

Чтение Content registry.

ctx.Storage

server

ctx.Storage:Register(name, schema)

Создаёт repository module.name. Требует persistence.write. Возвращает Get/Set.

server

ctx.Storage:Get(key, callback)

Читает из namespace самого модуля. Требует persistence.read.

server

ctx.Storage:Set(key, value, [callback])

Записывает в namespace модуля. Требует persistence.write; запись запрещена до activation staged context.

server

ctx.Storage:Transaction(statements, [callback])

Выполняет набор storage statements транзакционно через общий Storage layer.

ctx.Config:Register(schema)

Регистрирует конфигурацию модуля через Gincy.Config.

server

ctx.Console:Register(spec)

Подключает owned console command tree модуля к Gincy CLI.

Gincy.Schema

Validate(spec, value)

Проверяет и нормализует значение. Используется Content и Network.

Describe(spec)

Возвращает безопасное описание schema без function validators.

WalkReferences(spec, value)

Извлекает reference-поля для построения Content dependencies.

Поддерживаемые типы

В текущем Core присутствуют object, array, string/reference, enum, boolean, entity, vector, angle, number и integer/varint-представления, а также ограничения, заданные schema.

Gincy.Network

Request(peer, id, value, callback, timeout)

Request/response поверх зарегистрированного route.

SendRoute(...)

Низкоуровневая отправка route. Для обычного Module предпочтительнее Simple API.

RegisterState / PublishState / GetState

Replicated state с revision и onChange.

Dictionary / Intern / ResolveIdentifier

Словари повторяющихся идентификаторов и их revisions.

RegisterStream / SendStream

Передача больших payload частями с контролем состояния.

Snapshot()

Диагностический снимок сетевого слоя для Management/profiling.

Gincy.Content

Register / Unregister

Базовый content registry по kind + id. Для Module-owned регистрации используй MOD:Content или ctx.Content.

Get / GetAll / Exists / Find

Чтение и поиск зарегистрированного Content.

Content Runtime

Runtime поддерживает active instances, source precedence/dev override, dependencies, capabilities, human-readable failures, activation/replacement и cleanup. При замене instance его scheduler tasks отменяются по content generation.

Gincy.Modules

Get(id) / GetAll()

Состояние загруженных Modules.

Enable(id, callback)

Включает discovered Module с проверкой требований/зависимостей.

Disable(id, cascade)

Отключает Module; cascade учитывает dependents.

Reload(id, candidate)

Lifecycle-aware reload вместо ручного повторного include.

Dependents(id)

Возвращает обратные зависимости.

Gincy.Permissions

Has(ply, permission)

Проверяет permission через подключённые adapters/default policy.

RegisterAdapter(id, callback)

Подключает внешнюю систему прав. В Core предусмотрена интеграционная модель для популярных admin systems.

Gincy.Storage

Register(namespace, schema, generation) / Unregister(...)

Низкоуровневая регистрация repository.

Get / Set / Transaction

Асинхронные persistence operations.

Diagnostics()

Состояние persistence layer и диагностические метрики.

ShutdownModule / Shutdown

Очистка module-owned или всего Storage runtime.

Gincy.Config и совместимость

Gincy.Config.Register(moduleId, schema)

Регистрирует module config и применяет schema/default values через существующий Config layer.

Gincy.API.IsCompatible(...)

Проверка совместимости API/version contract. Product version и API/ABI/package/network версии не должны считаться одним и тем же номером.

CLI для разработчика и диагностики

CLI использует human-readable renderer; машинный вывод запрашивается через --json. Основные группы, присутствующие в текущем runtime:

gincy status
gincy doctor
gincy version

gincy module / modules
gincy content
gincy scheduler
gincy net
gincy storage
gincy package / packages
gincy deployment
gincy errors
gincy profile
gincy upgrade

Для начала проекта предусмотрен scaffolding уровня gincy create module <id> и создание Content templates для зарегистрированных типов.

Где что лежит

garrysmod/
├── gamemodes/gincy/          # runtime GLua
├── lua/bin/                  # native Gincy Core
├── gincy_dev/
│   ├── modules/              # открытые исходники модулей в разработке
│   └── content/              # development Content
├── gincy_modules/            # production .gmod
├── gincy_content/            # production editable Content
└── data/gincy/               # config/state/cache/identity/etc.

gincy_dev нужен для разработки. gincy_modules — для production Modules. gincy_content меняется независимо от .gmod. Runtime создаёт необходимые рабочие директории.
